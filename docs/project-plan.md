# Livelink PRD：个人 Wiki 与 AI 名片社交 MVP

## 1. 项目定位

Livelink 是一个 AI 个人 Wiki 与主动社交产品。用户提交基础资料和公开链接素材后，系统抓取并清洗素材内容，抽取事实、项目、技能、话题、可提供能力和想认识的人，构建结构化个人知识库，生成可编辑的个人 Wiki，并从 Wiki 派生适合扫码分享和社交转化的 AI 名片。

产品重点不是一次性生成一张漂亮名片，而是沉淀每个用户长期可复用、可追溯来源、可被搜索推荐的个人知识资产。AI 名片是个人 Wiki 的压缩展示层，服务于快速理解、扫码分享、搜索发现和连接转化。

## 2. 一句话描述

Livelink 把你的公开链接素材整理成个人 Wiki，再生成一张可分享、可搜索、可推荐、可连接的 AI 名片。

## 3. 当前阶段目标

当前阶段聚焦公开链接素材到个人 Wiki，再到 AI 名片和连接闭环：

```text
用户输入基础资料并粘贴公开链接
→ 系统抓取和清洗链接素材
→ AI 抽取事实、项目、技能、话题和需求
→ 生成结构化个人知识库
→ 生成个人 Wiki
→ 从 Wiki 派生 AI 名片
→ 用户编辑确认并发布
→ 他人浏览 / 扫码访问 / 搜索 / 推荐发现
→ 发起连接
→ 沉淀关系记录
```

阶段目标：

- 完成公开链接素材导入、抓取、清洗和入库。
- 完成 AI 知识抽取，生成可追溯来源的事实、项目和标签。
- 完成个人 Wiki 的生成、编辑、发布和公开展示。
- 完成从个人 Wiki 派生 AI 名片、二维码和分享页。
- 完成 Wiki / 名片搜索、推荐和连接申请。
- 验证用户是否愿意用公开素材构建个人 Wiki，并将其用于主动社交。

## 4. 核心价值

### 4.1 个人知识资产

传统名片和简介依赖用户手动总结，信息单薄且很快过期。Livelink 通过公开链接素材构建个人知识库，让用户的项目、文章、作品、观点、技能和需求沉淀为长期可复用资产。

### 4.2 可追溯的个人 Wiki

个人 Wiki 不是 AI 随机写出的长文，而是基于 source documents、profile facts 和 projects 生成的结构化页面。重要结论需要能追溯到公开链接或用户手动输入，降低“AI 编故事”的风险。

### 4.3 AI 名片作为社交转化层

个人 Wiki 负责深度理解，AI 名片负责快速展示。别人扫码后先看到适合社交场景的 headline、简介、标签、我能提供、我想认识和破冰话题，再按需进入 Wiki 深入了解。

### 4.4 搜索推荐和连接网络

当每个人都有结构化 Wiki 和名片后，系统可以基于技能、项目、话题、需求和可提供能力做搜索与推荐，让用户发现值得认识的人，并把一次性浏览转化为可沉淀的连接关系。

## 5. 目标用户

### 5.1 MVP 目标用户

- 创业者、独立开发者、AI 产品爱好者。
- 有 GitHub / Gitee、作品集、博客、公开文章或个人主页的人。
- 需要展示个人价值和寻找合作对象的人。
- 想主动发现同好、队友、投资人、客户或资源的人。
- 希望用更轻量方式替代简历、主页和自我介绍的人。

### 5.2 后续扩展用户

- 线下活动参与者。
- 学生、创作者、年轻职场人。
- HR、投资人、行业专家。
- 有人脉管理和关系沉淀需求的人。

## 6. 核心场景

### 6.1 用公开链接生成个人 Wiki

用户输入基础身份、我能提供、我想认识，并粘贴 GitHub / Gitee、作品集、博客、个人网站、公开文章、Notion 公开页等链接。系统抓取公开页面内容，清洗正文，抽取事实和项目，再生成个人 Wiki。

### 6.2 编辑确认个人 Wiki

AI 生成结果必须进入编辑确认页。用户可以删除、改写或隐藏任何事实、项目、技能、话题、需求和来源展示。发布内容以用户确认版本为准。

### 6.3 从 Wiki 派生 AI 名片

系统从个人 Wiki 中压缩出适合社交展示的 AI 名片，包括一句话定位、简介、标签、我能提供、我想认识、破冰话题和匹配关键词。名片用于扫码、分享、搜索和推荐。

### 6.4 搜索和推荐值得认识的人

用户可以搜索技能、项目、话题、需求和可提供能力，也可以进入推荐页查看系统给出的匹配对象和推荐理由。

### 6.5 发起连接和关系沉淀

用户从名片页、Wiki 页、搜索结果或推荐结果发起连接申请。系统记录连接来源、留言、状态和时间，形成后续关系管理基础。

## 7. 产品主闭环

1. 用户进入首页。
2. 用户点击“生成我的个人 Wiki”。
3. 用户填写基础资料，粘贴公开链接和补充说明。
4. 系统抓取公开链接并保存 source_documents。
5. AI 从素材中抽取 profile_facts 和 profile_projects。
6. 系统生成 profile_wikis.contentJson 和 markdown。
7. 用户编辑确认 Wiki。
8. AI 从 Wiki 派生 agent_profiles 名片草稿。
9. 用户编辑确认并发布名片。
10. 系统生成公开 Wiki、公开名片和二维码。
11. 他人通过扫码、搜索或推荐发现用户。
12. 他人发起连接申请。
13. 系统沉淀连接记录和推荐反馈。

## 8. 当前 MVP 范围

### 8.1 必做

| 模块 | MVP 范围 | 说明 |
| --- | --- | --- |
| 创建入口 | H5 首页和 `/create` | 移动端优先 |
| 基础资料 | 昵称、身份、城市、自我介绍、我能提供、我想认识 | 用于兜底和补充上下文 |
| 公开链接 | 多 URL 输入和用户补充说明 | 当前亮点入口 |
| 链接抓取 | GitHub / Gitee / 个人网站 / 博客 / 公开文章 / Notion 公开页 | 只抓公开可访问 URL |
| 内容清洗 | title、description、正文清洗 | 去脚本、导航、广告和明显噪音 |
| 知识抽取 | facts、projects、skills、topics、offers、wants | 每条重要事实保留来源 |
| 个人 Wiki | `contentJson + markdown` | 展示 overview、projects、skills、topics、offers、wants、sources |
| AI 名片 | 从 Wiki 派生 headline、bio、tags、icebreakers | 可编辑确认 |
| 公开页 | `/u/[slug]` 和 `/u/[slug]/wiki` | 可分享、可扫码 |
| 搜索 | Wiki 和名片关键词 / 标签搜索 | PostgreSQL 文本搜索优先 |
| 推荐 | 规则推荐 | 可解释理由 |
| 连接 | 连接申请和记录 | 来源记录 |
| 兜底 | 抓取失败、AI 失败、空数据兜底 | Demo 不断流 |

### 8.2 暂不做

- 完整微信小程序。
- 复杂账号体系。
- 自动抓取登录后内容或私密内容。
- 简历上传解析，作为后续扩展。
- 录音转写，作为后续扩展。
- 向量数据库和复杂语义搜索。
- 真正多轮 Agent to Agent 自动谈判。
- 精细权限系统。
- 活动管理后台。
- 付费和商业化闭环。

## 10. 输入与素材原则

MVP 的创建输入优先级是：

```text
基础资料必填少量字段
公开链接强推荐
用户补充说明兜底
简历和录音后续扩展
```

原则：

- 用户只靠基础资料也能继续创建，但产品亮点是公开链接素材生成 Wiki。
- 只使用公开可访问链接或用户主动补充的信息。
- 禁止抓取内网地址、本机地址和非网页协议。
- 不臆测敏感身份、收入、公司关系等事实。
- 区分事实信息、AI 推断标签和用户手动输入。
- 链接抓取失败时不阻塞创建流程。
- 用户必须能看到并编辑 AI 提炼结果。

## 11. 个人 Wiki 形式

个人 Wiki 同时以数据层和页面层存在：

```text
source_documents       原始公开链接素材
profile_facts          AI 抽取的结构化事实和来源引用
profile_projects       项目、角色、成果和技术栈
profile_wikis          Wiki contentJson、markdown、版本和状态
agent_profiles         从 Wiki 派生的 AI 名片
```

Wiki 页面建议结构：

```text
/u/[slug]/wiki
├─ Overview
├─ Projects
├─ Skills
├─ Topics
├─ Offers
├─ Wants
└─ Sources
```

## 12. AI 提炼后的编辑确认

AI 提炼不是最终发布结果，用户必须能在发布前继续编辑：

- Wiki overview、projects、skills、topics、offers、wants。
- 每条事实和项目的展示状态。
- 来源链接是否展示。
- 名片 headline、bio、tags、skills、interests、offers、wants、icebreakers。
- 是否发布 Wiki、名片或两者。

编辑确认页需要明确区分“AI 建议”“来源证据”和“用户确认内容”。发布时以用户确认内容为准。

## 13. 搜索与推荐规则

MVP 阶段采用可解释规则：

- 关键词命中 Wiki overview、projects、skills、topics、offers、wants。
- 关键词命中名片 headline、bio、tags、skills、wants、offers。
- wants 命中对方 offers/skills 加分。
- 技能互补加分，例如产品找开发、开发找设计、创业者找增长。
- 共同 topics 或 projects 加分。
- 同城市加分。
- 场景标签相同加分，但不是主条件。
- 已连接、已拒绝、自己本人过滤。

推荐结果必须展示一句自然语言理由，例如：

```text
你正在找 AI 工程化经验，对方的 Wiki 显示他做过模型接入和后端落地项目，也关注 AI 应用产品，可以从技术架构和产品落地聊起。
```

## 14. 视觉体验原则

- 移动端优先，适合微信内打开。
- 首屏强调“公开素材 → 个人 Wiki → AI 名片”。
- 创建流程短，尽量用示例链接和标签降低输入成本。
- 素材处理状态要清楚展示成功、失败和手动补充入口。
- Wiki 必须展示来源，增强可信度。
- 名片首屏必须清楚展示“我是谁、我能提供什么、我想认识谁”。
- 搜索和推荐结果要突出匹配理由，而不是只展示列表。
- 所有抓取和 AI 失败场景必须有 Mock / manual 兜底，不出现空白页。

## 15. 后续演进路线

### 阶段 1：个人 Wiki + AI 名片 MVP

- 公开链接素材导入。
- AI 知识抽取。
- 个人 Wiki。
- AI 名片。
- 搜索推荐和连接申请。

### 阶段 2：多源信息整合

- 简历上传和结构化提炼。
- 录音输入和转写。
- GitHub / Gitee / 小红书 / 作品集深度解析。
- 更完整的个人知识库版本管理。

### 阶段 3：分层授权与定向分享

- 公开信息与私密信息拆分。
- 面向投资人、HR、合作伙伴的定向 Wiki / 名片。
- 用户控制授权范围。

### 阶段 4：向量检索和 Agent 问答

- embeddings + pgvector。
- 基于 Wiki 的个人 Agent 问答。
- 更自然的语义搜索和推荐解释。

### 阶段 5：场景标签和活动网络

- 用户加入活动、黑客松、校园等场景标签。
- 同场景名片推荐。
- 场景内连接记录。

### 阶段 6：Agent to Agent 社交和 LBS

- Agent 自动匹配价值社交需求。
- Agent 先交换摘要和匹配理由。
- 用户确认后转化为 C2C 社交。
- 附近有价值用户推荐。
- 个人社交图谱和人脉管理。

## 16. 风险与应对

### 16.1 开发风险

| 风险 | 应对 |
| --- | --- |
| 创建流程过长 | 首版只保留基础字段和链接输入，其他字段可跳过 |
| 链接抓取失败 | 标记 failed/manual，允许用户手动补充摘要 |
| 小红书等平台反爬 | MVP 不承诺自动抓取，保存链接和用户说明 |
| AI 抽取不稳定 | 固定 JSON Schema，失败时使用 Mock 抽取 |
| AI 编造事实 | 要求来源引用，低置信度事实进入编辑确认，不自动发布 |
| 推荐结果为空 | 预置 Demo 用户、Wiki 和名片数据 |
| 搜索体验弱 | 先做关键词和标签搜索，后续再做向量检索 |
| 二维码访问失败 | 准备公开链接和本地 Demo 数据备用 |

### 16.2 产品风险

| 风险 | 应对 |
| --- | --- |
| 用户不知道为什么要建 Wiki | 首屏强调“让别人快速理解你，并找到值得认识的人” |
| 用户没有公开链接 | 基础资料和手动摘要可以兜底，但引导提供至少 1 个公开链接 |
| 用户不愿意公开全部内容 | Wiki 和名片都必须编辑确认，支持删除和隐藏来源 |
| 生成内容不像本人 | AI 提炼后必须进入编辑确认页，支持编辑、重生成和删除建议 |
| 过早锁定名片样式 | MVP 只做默认模板，文档和代码保留多模板扩展 |
| 搜索推荐不够精准 | 用明确标签、需求字段、Wiki topics 和可解释推荐理由补足 |
| 分享动力不足 | 强化 Wiki 可信来源、名片视觉、二维码和连接反馈 |
